# UI Component Architecture

## Status

Accepted for the demo implementation.

## Decision

Use shadcn/ui with its generated visual defaults for the demo. Preserve its interaction behavior and avoid bespoke branding work. Accessibility corrections required to meet the accepted WCAG 2.2 AA target—such as contrast, focus visibility, target size, or spacing—are mandatory and do not count as visual customization.

This is a visual shortcut, not an architectural shortcut. Feature code must depend on stable semantic components so a later Vantheon theme or component redesign does not require rewriting product workflows.

## Governing Rule

> Keep generic interaction behavior in shadcn primitives, product meaning in domain components, and visual identity in one theme boundary.

Do not create one giant component file. Use small files grouped by responsibility so components remain independently testable and replaceable.

### `components/ui`

- Contains source generated by the shadcn CLI.
- Contains generic interaction primitives only.
- Must not know about Champions, strategies, portfolios, runs, orders, trades, or versions.
- Must not read Zustand, TanStack Query, router state, WebSockets, or application services.
- Keep the generated visual defaults for the demo.
- Preserve public exports, refs, accessibility attributes, keyboard behavior, and `className` support when modifying a primitive later.
- Add only components the product uses; do not run `shadcn add --all`.

Examples: `Button`, `Dialog`, `Sheet`, `Tabs`, `Tooltip`, `Select`, `Popover`, `Table`, `Badge`, `Skeleton`, and `Textarea`.

### `components/system`

Contains small reusable components with application-wide semantics that are not financial entities.

Examples:

- `AsyncState` for loading, empty, failed, stale, and retry states.
- `StatusIndicator` for active, paused, degraded, disconnected, and failed states.
- `Money` and `Percentage` for consistent precision, sign, currency, and tabular numerals.
- `Timestamp` for consistent absolute and relative time display.
- `FreshnessIndicator` for last-update and stale-data communication.

Do not create one-to-one wrappers such as `AppButton`, `AppDialog`, or `AppInput` unless Vantheon needs a stable semantic contract beyond the underlying shadcn component. Empty wrapper layers make future work harder rather than safer.

### `components/domain`

Contains stable product concepts assembled from shadcn primitives and system components. These components protect feature screens from future visual redesigns.

Initial domain components should include:

- `ChampionWorkspaceSwitcher`
- `DraftIdentity`
- `CheckpointIdentity`
- `PortfolioVersionIdentity`
- `ConversationContextTarget`
- `StrategySemanticDiff`
- `PaperComparisonCard`
- `PortfolioOperationalStatus`
- `RunSummary`
- `RunDecisionTrace`
- `NoTradeExplanation`
- `PromotionReview`
- `EligibilityReview`
- `ComparisonValidityNotice`
- `ChampionRuntimeStatus`
- `PaperLifecycleControls`
- `LiveRiskSummary`
- `PauseExecutionsAction`
- `CancelOrdersAction`
- `StalePortfolioNotice`

Domain components accept semantic props rather than exposing their internal shadcn composition.

```ts
type ConversationContextTargetProps = {
  viewedContext: {
    kind: "draft" | "paper" | "live";
    label: string;
  };
  mutationTarget: {
    draftLabel: string;
    checkpointLabel: string;
  };
};
```

Feature code should not need to know whether this component currently renders a shadcn `Badge`, `Alert`, `Tooltip`, or a future custom visual treatment.

### `features`

Contains workflow composition, data hooks, commands, and route-specific behavior.

- Features may connect TanStack Query, Zustand projections, external subscription stores, and application services.
- Features pass normalized semantic data into domain components.
- Features must not embed authoritative strategy or portfolio mutations inside visual primitives.
- A feature may import a shadcn primitive directly for ordinary layout or forms when no reusable product meaning exists.

## Theme Boundary

Place the shadcn CSS variables in `src/styles/shadcn-theme.css` and import that file once from `src/app/globals.css`.

For the demo:

- Keep the generated shadcn colors, type scale, spacing, radii, shadows, and motion except where measured accessibility failures require a documented token or component correction.
- Use semantic utilities such as `bg-background`, `text-foreground`, `text-muted-foreground`, `border-border`, and `ring-ring`.
- Do not add hard-coded hexadecimal colors, page-specific theme overrides, or selectors that depend on shadcn's internal DOM structure.
- Do not use color alone to distinguish Draft, Paper, Live, risk, freshness, or operational state. Retain explicit labels and icons even before visual customization.

Future customization begins in this file. Token-only changes must not require edits to features or domain component APIs.

## Component Usage Rules

### Prefer composition over modification

Build domain meaning around primitives before editing the primitive itself.

```tsx
// Correct: domain meaning is owned here.
function PauseExecutionsAction(props: PauseExecutionsActionProps) {
  return (
    <AlertDialog>
      <AlertDialogTrigger asChild>
        <Button variant="destructive">Pause executions</Button>
      </AlertDialogTrigger>
      {/* Domain-specific confirmation and consequences. */}
    </AlertDialog>
  );
}
```

Do not add `portfolioId`, `strategyVersion`, authorization checks, or financial commands to `components/ui/button.tsx`.

### Preserve semantic APIs

Domain props describe what something means, not how it looks.

Prefer:

```ts
<PortfolioOperationalStatus status="degraded" />
```

Avoid:

```ts
<PortfolioOperationalStatus color="orange" icon="warning" pulse />
```

The first API survives a redesign. The second leaks the current presentation into every caller.

### Keep formatting centralized

Financial values must not be formatted ad hoc inside cards or tables. Use shared formatters and system components for:

- Currency and locale.
- Positive and negative signs.
- Percentage precision.
- Missing and stale values.
- Market timestamps and user time zones.
- Large-number abbreviation.

### Keep state ownership outside visual primitives

- Shadcn primitives may own temporary interaction state such as whether a popover is open.
- System and domain components may own local presentation state.
- Server-backed and financial state remains in its declared query, command, or subscription owner.
- Passing a portfolio value into a component does not make that component authoritative for the value.

## Tables, Charts, and High-Frequency Surfaces

- Use the shadcn `Table` only as presentational markup.
- Use TanStack Table and virtualization for sorting, filtering, selection, large histories, positions, orders, and runs.
- Keep column definitions and domain cell renderers outside `components/ui/table.tsx`.
- Use Lightweight Charts for live financial charts rather than shadcn's general chart component.
- Keep chart instances behind stable domain adapters so a later visual redesign does not change transport, caching, or subscription code.
- High-frequency updates must reach only subscribed cells or chart series; they must not rerender the entire workspace shell.

## Conversation Components

Use shadcn primitives for the composer controls, menus, dialogs, scroll areas, and basic message layout. Keep these as domain components:

- Structured Champion progress.
- Strategy change proposals.
- Semantic diffs.
- Backtest and run results.
- Trade or allocation proposals.
- Viewed-context and mutation-target labels.
- Approval and promotion actions.

Conversation rendering must not directly apply strategy mutations. It renders server-authoritative command and patch states.

## Customization Path After the Demo

Customization should proceed without changing product behavior:

1. Update tokens in `shadcn-theme.css` for color, typography, radius, density, focus, shadow, and motion.
2. Update shadcn primitive internals while preserving their exports and public props.
3. Redesign domain component internals while preserving semantic prop contracts.
4. Update feature layouts only when the information architecture changes, not merely because the brand changes.

Avoid a broad rewrite. Each stage should be independently reviewable and covered by visual regression tests.

## Review and Test Requirements

- Render representative states for every domain component: normal, loading, empty, stale, degraded, failed, and unauthorized where relevant.
- Test keyboard navigation, focus restoration, dialog labelling, screen-reader names, and reduced motion.
- Add Playwright visual snapshots for the Draft, Paper, Live, run-detail, promotion, and emergency-control surfaces.
- Test light and dark modes even while using stock shadcn tokens.
- Audit actual stock token contrast, focus-obscuration behavior, and interactive target size before claiming WCAG 2.2 AA; do not assume library defaults establish conformance.
- Verify narrow and wide layouts, including collapsed and expanded conversation panels.
- Run the backend stress simulator while exercising domain components to ensure visual customization boundaries do not introduce broad rerenders.

## MVP Acceptance Criteria

- The demo uses recognizable stock shadcn styling with no bespoke branding work; documented accessibility corrections are allowed and required.
- No feature-specific financial logic exists in `components/ui`.
- Draft, Paper, and Live remain distinguishable through words, icons, and context—not custom color alone.
- All financially consequential actions use domain components with explicit confirmation and state feedback.
- Changing theme tokens does not require changes to feature code.
- Replacing a shadcn primitive does not change domain component callers.
- Charts, tables, and streaming stores remain independent from the visual theme.
